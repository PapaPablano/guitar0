Grounding Context

Search today. engine-client.ts:79-88 posts /api/search with limit: 15. The query box starts empty (StemPanel.tsx:54) although the tab's title and artist are already in hand (App.tsx:776, used only for the Songsterr link). Search runs only on form submit, with no stale-response guard (StemPanel.tsx:188). Results are ranked by |duration - tab length| alone (stem-controls.ts:113-120); title and uploader are never used.

Engine facts the verifier added. The pinned engine's MAX_LIMIT is 15, so widening the field takes several queries, not a bigger limit. It already caches results for 60 seconds. Items already carry thumbnail, and uploader falls back to the channel name, so "Artist - Topic" channels are visible. Extraction is flat, so there is no description, upload date or view count. An audition route, GET /api/search/preview, already exists.

Sync today. Stems imported from YouTube skip alignment: detect and reuse run only for the user-recording clock (App.tsx:446,454). The alignment code takes any decodable Blob (alignment/analyze.ts:56-70) and stems.clock.setAlignment already exists (stem-mix.ts:144), so the blocker is plumbing typed to UserAudioClock. Per-song memory is keyed by file hash (recording-profile.ts); a YouTube import has only a url: key in the saved-stems index. The plan defers per-song mixer memory and multi-point anchors.

Boundaries. Results are ranked, never filtered. The rights notice stays beside search. No change to how stems are separated or what the YouTube option may import. YouTube is desktop-only.

External. Soundslice auto-aligns then lets the user fix a few syncpoints; chroma plus DTW (librosa, FMP) aligns two recordings of one piece; spotDL and somedl pick YouTube results by scoring and prefer official audio. Research value was moderate; Soundslice and spotDL details were not confirmed at source.

1. Auto-align YouTube stems to the tab

Axis: Timing syncConfidence 80%Complexity Medium
Description
After a YouTube import, run the existing bar-level alignment on the separated stems, as is done for a user's own recording. The likely input is the summed non-guitar mix, since the tab's rendered guitar is what the "other" and "guitar" stems contain and drums or bass alone are thinner evidence. The result sets the offset and bar timeline, so a live-album take with a long intro lands on the beat with no slider. A per-bar map also gives a tempo ratio, which covers the "set tab tempo to match the recording" idea without a separate feature.
Basis
direct: App.tsx:446 and :454 gate detect and reuse on userClockRef.current === clockForLoad; OffsetSlider.tsx:27 says offset controls follow "the recording alone: not the desktop bridge, not stems". The verifier read alignment/analyze.ts:56-70 (takes a file: Blob) and confirmed stems.clock.setAlignment exists. external: Soundslice auto-align then fix; chroma plus DTW with open-end DTW for long intros (librosa, FMP).
Rationale
YouTube audio is the source most likely to differ from the tab in intro, outro and sections, and today the player fixes that by hand or not at all. This is the gap the research named: nobody pairs right-recording search with automatic alignment. Ideas 4 and 5 both build on its result.
Downsides
Alignment on a different recording than the tab's reference (live, different arrangement) is the open risk, so it needs a feasibility spike on real takes first. startAlignment, alignRequest and stillCurrent are typed to the recording clock (App.tsx:126,299,340-355) and persistence is hash-keyed, so a url: path is new work. Stem audio export also ignores the alignment map today (App.tsx:1075-1082), so an aligned YouTube mix would play differently from how it exports; that needs a warp-aware render.

2. Score results on trust signals, and show why

Axis: Picking the right recordingConfidence 85%Complexity Low
Description
Replace rankByLength with a pure scoreResult(item, tabMeta). Length gap stays the main term. Add a boost for "- Topic" uploaders and for an uploader or title that matches the tab's artist and title, and a penalty for live, cover, lyric, karaoke, tutorial and remix in the title. Each row shows its length gap against the tab ("+0:12"), one reason badge, and the thumbnail the engine already sends. Everything stays listed; only the order changes. Memoize the sort instead of redoing it every render. Record real engine responses as test fixtures so weights can be tuned against them.
Basis
direct: stem-controls.ts:113-120 ranks on Math.abs(duration - tabSeconds) only; searchRow (:97-106) shows only uploader and duration; SearchItem (engine-client.ts:41-48) has no thumbnail though the test fixture sends one (engine-client.test.ts:110). The verifier confirmed the engine returns thumbnail and a channel-name uploader. external: spotDL scored selection; somedl prefers official audio.
Rationale
A live or lyric upload 3 seconds from the tab's length currently outranks the studio cut 8 seconds away, and a wrong pick costs a download and a separation. It needs no engine change and stays inside "ranked, not filtered".
Downsides
The weights are a product judgment and will need tuning. "Provided to YouTube by" cannot be used: the engine's flat extraction returns no description. Title heuristics fail on songs that legitimately have "Live" or "Remix" in the name, which is why they should be penalties and not filters.

3. Search starts from the tab, with query variants

Axis: Candidate retrievalConfidence 85%Complexity Low
Description
When YouTube is chosen on a loaded tab, fill the box with the tab's title and artist and search at once. Run two to four variants in parallel (plain, plus "official audio", "- Topic", "instrumental") and merge by URL, so the field is wider than the engine's hard 15. The box stays as an editable override. Add a request id so a slow older response cannot overwrite a newer one, and an abort signal.
Basis
direct: StemPanel.tsx:54 useState(''); App.tsx:776 builds the Songsterr link from timeline.title and timeline.artist; StemPanel.tsx:188 setResults(await client.search(query)) has no guard; engine-client.ts:51 says "Ranking by length needs a wide field to find a close match". The verifier confirmed MAX_LIMIT is 15.
Rationale
The first step today is retyping a song the app already knows. Merged variants feed idea 2 a better field, which is the same reasoning the plan used to pick 15 over 8.
Downsides
Closer to an obvious fix than a big bet. Skip a client-side result cache and a timeout: the engine already caches for 60 seconds. Several parallel searches may hit the engine's 3-wide limit and rate limits, so cap the variants. A tab with a poor title gives a poor seed, which is why the override matters.

4. One song record: remembered pick, offset, mix, and past imports

Axis: Reliability and per-song memory (with Import hand-off)Confidence 70%Complexity Medium
Description
Keep a record per song holding the chosen URL, the stem job, the offset or alignment from idea 1, the mixer state and the URLs the player rejected. Reopening the tab offers "Used last time" first, with the mix and timing restored and no search. Store title, uploader and duration with each saved-stems entry too, so "Already made" matches show above results before any network call and work offline.
Basis
direct: recording-profile.ts:66-69 holds offset and mix but is keyed by file content hash; StemPanel.tsx:176 keys a YouTube import as url:${item.url} only; saved-stems.ts:14 maps a hash to a job with no metadata; the backing-track plan lists "Remembering mixer settings per song" as deferred (:100).
Rationale
Players come back to the same few songs, and the whole search, import and nudge routine repeats every session. The best search is the one that never runs, and it also shields the player from yt-dlp breakage.
Downsides
The key is the real decision: tab title, URL or hash. Titles get edited and tabs get re-saved, so tab identity is fragile. Decide it once and persist idea 1's alignment under the same key. The portable sidecar-file variant is optional and widens scope.

5. "Doesn't match the tab, try the next one"

Axis: Picking the right recording (with Timing sync)Confidence 65%Complexity Medium
Description
Once idea 1 exists, a poor alignment result (not-found or inconsistent) becomes a plain verdict on the panel: "This doesn't line up with the tab. Try the next result." One click imports the next-ranked candidate. Rejected URLs are remembered in the song record from idea 4 and sink in later rankings.
Basis
direct: auto-align.ts:89 returns { phase: 'not-found', reason: 'inconsistent' } with remember: true; alignment-controls.ts:38-40 already has graded verdict text. external: cover-song identification compares chroma to tell an original from a cover.
Rationale
Length and title are weak proxies for "right recording"; alignment against the player's own tab is a direct test. It turns the wrong-version trap into a one-click retry.
Downsides
The verdict only arrives after a download and a separation, which costs minutes. A fully automatic "Find it for me" loop that imports candidate after candidate was cut for that reason; keep the retry manual. Depends on idea 1. The fix for a failed verdict should never silently discard a take the player likes.

6. Search health check and plain errors

Axis: Reliability and per-song memoryConfidence 80%Complexity Low
Description
When the engine is ready, run one known-good search (ytsearch1:) and show the result in the engine state line. If it fails, say "YouTube search isn't working in this engine build" and keep the box disabled with that reason, instead of letting the first real query end in "No results" or a raw engine string. Map engine errors to named states (search broken, rate-limited, offline) with a Retry, and add a timeout and cancel to the search request.
Basis
direct: ytdlp_fix.py:15-17 is except ImportError: return, silent; engine-client.ts:163-171 returns body.detail to the UI verbatim; engine/tests/test_ytdlp_fix.py:8 is pytest.importorskip("yt_dlp"), so the tests skip silently; engine-client.ts:139-149 passes no signal on the search path.
Rationale
The feature depends on a private-globals patch to yt-dlp, which breaks on its own schedule. The player should hear "search is down, not your query" before typing.
Downsides
Reads as a backlog fix more than a direction, but it is cheap and protects every other idea here. A probe adds a request at startup, and it can pass while real queries still fail.

7. Tap-to-sync points as the manual fallback

Axis: Timing syncConfidence 55%Complexity High
Description
When automatic alignment is low-confidence, let the player tap two or three bars while the track plays and bend time between them (a ground-control-point fix, as in Soundslice's syncpoints), with detected beats shown and snapped to. It covers a studio intro, an extra chorus or a fade the tab does not have, for any source.
Basis
direct: the stem-separation plan says "Multi-point anchors are deferred. The user sees a constant shift, not drift." (2026-10-04-0945…:67); alignment-controls.ts:70 is showOffset: !ctx.hasTimeline && !running, hiding the one manual control once a timeline commits; OffsetSlider.tsx:76-78 notes that a recording that speeds up or slows down will still drift. external: Soundslice syncpoints, beat overlay and snap.
Rationale
Idea 1 will not always succeed, and today a failure leaves a single offset slider that disappears when a timeline commits.
Downsides
It reopens an item the plan deferred on purpose, and it is a large change to the UI and the tab clock. Treat it as a scope decision after idea 1 shows how often alignment fails.
